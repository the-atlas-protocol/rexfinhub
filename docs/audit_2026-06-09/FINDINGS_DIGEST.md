### SEC SCRAPER (etp_tracker/)

The scraper is a four-tier detection stack plus a batch pipeline, all converging on the same SQLite tables. Tier 1 (atom_watcher.py, 60s systemd daemon) polls the EDGAR getcurrent atom feed for 485*/497*/N-1A/N-2 across all filers and inserts raw filing_alerts; Tier 2 (single_filing_worker.py, 30s daemon) enriches each alert by reusing step3's strategy dispatch, auto-creating trusts (source='watcher_atom') and writing filings + fund_extractions + lightweight PENDING fund_status placeholders; Tier 3 (reconciler.py, 08:00 ET oneshot) diffs the SEC daily form index against filing_alerts as a safety net and runs REX-lifecycle steps (mkt PEND→ACTV, CIK backfill); Tier 4 (bulk_sync.py, weekly) stubs new filers from company.idx. The batch path (run_pipeline.py, driven by the 15-min fresh-poller and the 4x/day intraday-refresh fallback) loads the curated+watcher_atom universe (~525 CIKs) from the trusts table, pulls submissions JSONs (step2 → CSV1/CSV2 filtered by is_prospectus_form: 485*/497*/N-1A*/S-1*/S-3*/EFFECT/POS AM), extracts per-filing with manifest-gated incremental processing (step3: header_only for 485BXT/497J, s1_metadata for S-1/S-3/POS AM/EFFECT, full SGML+body+iXBRL otherwise), rolls up fund status (step4: PENDING/DELAYED/EFFECTIVE post the 2026-06-09 overhaul) and name history (step5), then sync_service.py upserts the CSVs into filings/fund_extractions/fund_status/name_history, after which sync_rex_products_from_filings (promote-only) and webapp's status_reconciler drive rex_products/status_history. Tickers come, in declining reliability, from SGML CLASS-CONTRACT-TICKER-SYMBOL headers, title-paren matches, and a ±600-char label window with per-filing dedupe; effective dates come from the SGML EFFECTIVENESS DATE header, iXBRL ProspectusDate, and a HIGH/MEDIUM regex cascade — though in code iXBRL and HIGH-regex can override the header. Rate limiting is per-process only (0.25-0.35s pauses, 8 req/s async limiter, Retry on 429) with no cross-daemon coordination. The biggest live defects: the Tier-3 reconciler reads daily indexes through a no-TTL cache so its backstop is blind to late-day filings; step3 records fetch failures as permanent success via a placeholder row (4,549 NONE extractions); 91% of DELAYED rows lack the 485BXT delayed-to date the launch-race work needs; and 33-Act S-1/EFFECT competitor filings (crypto, ProShares Trust II-class leveraged products) have no fast detection lane and surface in fund_status as trust-named ticker fan-outs.

### ORCHESTRATION / PROCESS (scheduled entry points, daily dependency chain, multi-writer coordination)

The daily engine is a federation of ~15 systemd timers plus two cron jobs, not a single pipeline. SEC ingestion runs on three pathways: the atom watcher daemon writes filings/fund_extractions/fund_status directly to the DB via single_filing.py; the fresh-poller (every 15 min, 08:00-20:45 ET) re-scrapes CSVs via etp_tracker/run_pipeline.py and then runs sync_rex_products_from_filings.py --apply (the only scheduled rex_products writer from SEC data); the intraday-refresh timer (08:05/12:05/16:05/20:05) wraps run_daily.py and skips the whole SEC half whenever the fresh-poller log is <30 min old. Bloomberg lands at 17:15+21:00 via rexfinhub-bloomberg-chain.service, whose ExecStartPost wrapper (apply_bloomberg_post_steps.py) is now the real nightly brain: fund_master → ensure_canonical_identity → underlier overrides → issuer brands → classification sweep → classification overrides → refresh_effective_dates --apply → status_reconciler --apply. So the status reconciler IS on a schedule, but only as a parasite of Bloomberg-pull success and only Mon-Fri. The send path is preflight 18:30 (writes token + auto-GO decision) → gate-open 19:00 → run_daily --skip-sec at 19:30 which waits and calls send_all.py --use-decision --send → gate-close 20:00 → pipeline_summary cron 20:15. Render publication is scattered across five uploaders (fresh-poller conditional, intraday, daily, prebake, and the 03:00 CBOE unit's trailing run_daily --upload). ### live_feed.db — second runtime database deliberately excluded from the upload/replication cycle

The live feed is a deliberately isolated real-time notification lane: the VPS atom watcher (60s SEC poll, 485/497/N-1A/N-2 forms only) fire-and-forget POSTs each new filing to Render's /api/v1/live/push, which UPSERTs by accession_number into a one-table SQLite file at data/live_feed.db, bound to its own SQLAlchemy engine (LiveFeedBase) precisely so the daily wholesale etp_tracker.db swap cannot wipe it; the Tier-2 enrichment worker re-UPSERTs the same row with resolved trust links a minute later. Every page on rexfinhub.com loads live-feed.js, which polls the unauthenticated /api/v1/live/recent every 30s and toasts new rows. Growth is bounded by design — an opportunistic prune keeps ~500 rows — so the 'unexamined growth' concern from the brief is actually closed; the file is and will stay tens of KB. Durability is the real gap: the only populated copy lives on Render's persistent disk (starter plan, no snapshots), outside the VPS 23:00 backup, the D-drive sync, and every DB audit — an accepted loss that was flagged in a raw audit on 2026-05-05 but never promoted into SYSTEM.md, GLOSSARY, or an ADR; in fact the entire subsystem is invisible to the six-doc framework. Migration 003 (dropping the fossil live_feed table from the main DB) is verified applied — the 711MB prod mirror has no live% tables. ### Backup/restore procedures (VPS nightly DB backup, D-drive archive chain, rollback snapshots, restore path)

The entire backup posture protects one file — data/etp_tracker.db (745MB, WAL mode, confirmed via read-only PRAGMA) — through three loosely-coupled layers, none of which has a restore procedure. Layer 1: rexfinhub-db-backup.timer fires at 23:00 ET and runs a sqlite3 .backup into data/backups/etp_tracker_YYYYMMDD.db on the SAME VPS volume as the live DB, then prunes files older than 7 days (prune is &&-gated on backup success). Layer 2: laptop-side pull scripts copy backups to the D: drive — sync_vps_to_d_drive.sh (23:30, pulls the consistent .backup snapshots from data/backups, additive forever per ADR 0003) plus two near-duplicate PowerShell scripts (sync_vps_to_d.ps1 scheduled, sync_vps_to_d_on_demand.ps1 interactive) that instead hot-scp the LIVE WAL-mode DB without its -wal file into a second, different D: location. Layer 3: a backup_recent assertion in scripts/run_assertions.py checks freshness at 08:00, but its alert email dies exactly when an assertion fails (ExecStartPost not failure-tolerant, per OPERATIONAL_RECON.md C) and its glob accepts any etp_tracker*.db* file including rollback snapshots. Separately, several write-scripts create pre-write rollback snapshots in data/backups with keep-3 rotation — but a VPS-crontab disk-hygiene cron (added during the June disk-full emergency, existing only on the VPS, not in the repo) deletes *_pre_*.db files every 15 minutes, voiding that safety net. There is no documented restore path anywhere: the only mention in the entire repo is an unchecked TODO in docs/raw/legacy/ROADMAP.md:540, and a real restore is non-trivial because 4 long-running daemons hold the DB open in WAL mode. Retention is described three different ways across docs (7-day in the unit and systemd README, 14-day in SYSTEM.md and ADR 0007, keep-last-10 in an undocumented cron). Offsite coverage depends entirely on Ryu's laptop being online with the D: drive attached within the ~8-day VPS retention window; the only other off-VPS copy is the Render replica (same-day, no history, reachable only via the upload API flagged as security GAP-03).
